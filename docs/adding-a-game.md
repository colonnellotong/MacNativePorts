# Adding a game

This is the long form of "copy `games/dora/` and start changing things". It is written in the order
the work actually has to happen, and each stage says what it produces and how you know it worked.
The numbers quoted are `dora`'s, as a sense of scale.

## What you need

- Your own copy of the game (XCI or NSP) and `prod.keys` dumped from your own console.
- Xcode Command Line Tools — `xcrun clang`, no SDK, no Homebrew packages.
- Python 3 for the scripts under `shared/scripts/` and `games/<code>/scripts/`.
- The rewrite stage is done by MacNativeGames' `build_app.py`. This repository starts where that
  leaves off: it consumes its `rewritten/` output.

## Stage 1 — Container and ExeFS

Program NCAs are usually Block-compressed (`.ncz`) inside the container; `nsz -D` expands them, and
nothing in the pipeline can read the compressed form. `dora`'s 2,390,039,552-byte container becomes a
2,389,344,256-byte Program NCA, 19 seconds.

Extract the ExeFS modules: `main`, `sdk`, `subsdk0`, `rtld`, plus `main.npdm`.

`games/dora/scripts/extract_exefs.py` does this and verifies the FS header, the ExeFS hash table and
every data block as it goes. RSA signatures are not checked — they would need Nintendo's public key
and prove nothing about your own dump.

**Produces:** `<work>/10_extracted/exefs/`.
**Check:** every module's SHA-256 matches what a second extraction gives.

Worth doing early: compare your `rtld` against another game's. `dora`'s and Bayonetta 3's are
byte-identical, which means the same NintendoSDK version and the same host ABI — one less thing to
worry about for the whole rest of the port.

## Stage 2 — The ARM64 rewrite

The console allows some things macOS does not: `svc` calls that the host has no equivalent for, and
reads of the cycle counter that are not allowed from user space. Those sites get rewritten. For
`dora`: 45,937 sites across three modules.

Every rewrite is checked by running both the original and the rewritten instruction sequence on the
same inputs — 141,209 equivalence trials, of which 120,001 are valid (the rest cannot be evaluated
without device state). Any disagreement is a hard failure.

118 sites are gated rather than rewritten (76 `svc`, 42 `cntpct`): the gate records that the game
reached them and hands control to the host, so an unhandled call surfaces as a named failure instead
of a crash.

**Produces:** `<work>/20_rewritten/{main,sdk,subsdk0,rtld}`.
**Check:** zero disagreements, and re-running produces byte-identical output.

## Stage 3 — Modules, symbols, relocations

Each module imports what the others export, plus what the host answers. `dora` has 9,489 imports
across three modules; all but one resolve from cross-module exports, the host override table, or a
linker boundary marker. One needs a hand-written stub.

530,622 relocations, of which 474,400 are plain relative ones that need no symbol at all — the rest
are resolved from the tables above.

`shared/scripts/map_modules.py` and `plan_loader.py` build this; `got_symbols.py` and
`lookup_symbol.py` answer "where does this name actually come from" when one does not resolve.

**Produces:** `runtime_tables.h` (modules, symbols, relocations, gates).
**Check:** `verify_fs_coverage.py` style coverage reports — every import accounted for, none guessed.

## Stage 4 — The filesystem surface

The game asks for files through `nn::fs`. On the console that is the RomFS partition and SaveData;
here it is a mount point over the extracted RomFS plus a directory on the host, and `fs_host.c` is
what answers.

For a Unity title this is the stage that grows: IL2CPP and Addressables reach for paths in patterns
that a hand-written engine never does. `dora` needed `dora_fs_ext.c`, 47 service permissions, and
RomFS read-only access with no SaveData permission at all — its saves go through the host mount.

RomFS itself is indexed by `runtime-index.bin`, generated by `make prepare` and size-and-hash
checked against `assets/expected-*.json` on every start.

**Produces:** `romfs_config.h`, `shared_fonts_config.h`, and the index beside the RomFS image.
**Check:** the game reaches its own title screen.

## Stage 5 — The first frame

This is where NVN shows up, and where most of the work is. In order:

1. **The window.** A real `CAMetalLayer`, not the headless surface the host starts with.
2. **What the game calls.** Record every NVN entry point the game actually reaches. `dora` asked for
   532 names; the shared layer already answered most of them.
3. **The one that is not there.** For `dora` it was `nvnCommandBufferDownsample`, which Unity calls
   once per frame. `dora_nvn.c` translates it into a `CopyTextureToTexture` record rather than
   letting it die at the unimplemented stub.
4. **Shaders and textures.** The translator service needs `totk_xlate` and `spirv-cross` built and
   in `build/`; without them nothing renders and the log says so.
5. **Synchronisation.** MSAA resolve was the last blocker here — see `patches/README.md`.

**Check:** frames advance with no `【红】` in the log, and a screenshot shows the game rather than a
flat colour.

## Wiring it into this repository

```
games/<code>/
  game.mk            title, title id, EXCLUDE_SRC, GAME_WORK
  assets/            expected-<version>.json — sizes and hashes prepare checks against
  scripts/           prepare_runtime.py (adapted from dora's)
  runtime/           only the files that differ from shared/runtime
```

`make prepare GAME=<code>` and `make runtime GAME=<code>` are the whole interface. `make list
GAME=<code>` prints how many files the overlay replaces.

### The one rule that bites

**A game-specific configuration header must not also exist in `shared/runtime/`.**

Shared `.c` files include their headers with quotes, which searches the including file's own
directory first. If `shared/runtime/game_version.h` exists, `shared/runtime/romfs.c` gets *that* copy
no matter what `-I` order says — and a game's `-I` never wins.

This cost a build here: the shared tree still carried Bayonetta 3's `game_version.h`
(`TOTK_GAME_DIR "v120"`), so `dora` looked for its RomFS under `extracted/v120/` and reported
`RomFS index missing` while the data sat in `extracted/v0/`.

Rules that follow from it:

- Configuration headers (`game_version.h` and friends) live in `games/<code>/runtime/` only.
- A shared header may declare defaults under `#ifndef`, but must not define a value a game needs to
  override.
- `runtime.h` is shared only. Two copies collide under `#pragma once`, which deduplicates by path —
  the game's copy and the shared copy are different paths, so both get included and the typedefs
  clash.
